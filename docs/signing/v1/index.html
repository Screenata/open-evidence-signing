§ 0
Orientation — What OES Is
PRIMER

The Open Evidence Signing Specification (OES) defines a format and protocol for cryptographically signing compliance evidence so that any third party — auditors, GRC platforms, regulators, automated tools — can independently verify the integrity, provenance, and temporal ordering of evidence artifacts without access to the originating system.

It combines three standard primitives: a SHA-256 content hash, a digital signature (RSA or ECDSA) over a canonical JSON subject, and an RFC 3161 timestamp from an independent Time Stamping Authority. The result is a single JSON document — the Evidence Signing Envelope (ESE) — that is tamper-evident, attributable, and anchored in time. A conforming verifier can be written in under 200 lines in any language with a standard crypto library.

§ 1
The Evidence Signing Envelope (ESE)
ENVELOPE

The ESE is the core artifact. It is a JSON document with four top-level blocks: the spec marker (@context, version, id), the issuer, the subject (what is being proven — including the content hash and metadata), and the proof (the signature and timestamp). The signature covers only the subject block; everything else is routing or attestation about the signature itself.

Fig 1.1 — ESE structure. Solid double border = the canonicalized subject the signature covers.

Important Property — the signature is scoped to subject

proof.signedFields = "subject". The proof block and the outer routing fields are not signed. This is deliberate: a verifier can rewrite proof.timestamp (e.g. re-fetch a TSA token) or change issuer.name for display without invalidating the proof. Anything an auditor must trust — the content hash, the framework, the control reference — lives inside subject.

§ 2
Signature Computation & Canonicalization
SIGNING

The signature is computed over a canonical representation of the subject object, not its raw on-disk JSON. JSON key ordering is not guaranteed by the spec, so re-serializing the same logical object can produce different bytes and break verification. Canonicalization removes that ambiguity.

Supported algorithms

Algorithm IDproof.typeKey Type
RSA-SHA256RsaSignature2024RSA — 2048-bit min, 4096-bit recommended (RSASSA-PKCS1-v1_5)
ECDSA-SHA256EcdsaSignature2024EC P-256 (secp256r1)

Canonicalization — sorted-keys-2space

Extract subject → serialize to JSON with recursively sorted keys and 2-space indentation → encode as UTF-8 bytes. That byte sequence is the signing input. Sorted keys with 2-space indent were chosen over pure compaction (or RFC 8785 JCS) for human readability while debugging.

function stableStringify(obj) {
  if (obj === null || typeof obj !== 'object') return JSON.stringify(obj);
  if (Array.isArray(obj)) return '[' + obj.map(stableStringify).join(',') + ']';
  const keys = Object.keys(obj).sort();
  return '{' + keys.map(k => JSON.stringify(k) + ':' + stableStringify(obj[k])).join(',') + '}';
}

Content hash & fingerprint rules

  • Single file: SHA-256 of the file bytes.
  • Bundle (ZIP): SHA-256 of the entire ZIP bytes; per-file hashes go in subject.files[].
  • Structured data: SHA-256 of the exact bytes as stored/transmitted — no normalization.
  • Fingerprint: hex(SHA-256(pem_public_key)).substring(0, 16), PEM including BEGIN/END delimiters, LF line endings.
Gotcha — hash the exact bytes, never a re-encoding

For structured formats (JSON, XML, CSV) the hash covers the precise bytes the recipient receives. Semantic equivalence is not sufficient — re-serializing a JSON file with different whitespace yields a different hash. Likewise, re-zipping the same logical bundle with different compression settings changes the bundle hash. This is intentional: artifacts are identified by their bytes, not their logical content.

§ 3
Key Discovery Protocol
DISCOVERY

A verifier needs the issuer's public key to check a signature. OES uses a well-known endpoint convention so no out-of-band key exchange is required. Issuers MUST serve a JSON document at:

GET {issuer.id}/.well-known/oes-signing

The document lists every key the issuer has used, each tagged with a fingerprint, algorithm, publicKeyPem, validity window, and a revoked flag. The verifier picks the entry whose fingerprint matches proof.publicKeyFingerprint.

// key matching during verification (§5.3)
doc = GET {issuer.keyDiscovery} // MUST be HTTPS in production
key = doc.keys.find(k => k.fingerprint === proof.publicKeyFingerprint)
if !key:
  → FAIL("unknown signing key")
else if key.revoked === true:
  → FAIL("signing key revoked")
else if key.validTo && key.validTo < now:
  → WARN("expired") // cleared if a valid TSA timestamp predates validTo (§7.5.8)
else:
  → use key.publicKeyPem for verification

Operational rules

  • Rotation: old keys MUST remain in keys[] (with original dates) until all evidence signed with them is past retention. Issuers SHOULD set validTo or revoked: true rather than deleting keys.
  • Caching: verifiers SHOULD cache discovery docs ≥ 1 hour and ≤ 24 hours; endpoints SHOULD send Cache-Control.
  • BYOK: customer-managed keys appear in the same document alongside platform keys; the envelope's fingerprint routes to the right entry. Issuers MAY scope with ?org={orgIdentifier} — an optional extension verifiers fall back from to the base path.
  • Offline: once a key is cached, all subsequent envelopes signed by it verify with no network access (§7.3).
§ 4
RFC 3161 Timestamp Binding
TIMESTAMP

An RFC 3161 timestamp proves the signature existed at a specific point in time, as attested by an independent TSA. This prevents backdating and provides a legally recognized temporal anchor under eIDAS and similar frameworks. Critically, the timestamp is taken over the signature bytes — not the content — so it binds the act of signing, not the artifact alone.

Fig 4.1 — RFC 3161 request/response (§6.2) and what the verifier re-checks

The spec mandates no single TSA. Issuers SHOULD use multiple TSAs with fallback for reliability. Verifiers allow 5 minutes of clock skew and MAY optionally verify the TSA certificate chain against known roots.

§ 5
Verification Algorithm — Envelope to Verdict
VERIFY

This is the normative procedure. A compliant verifier MUST implement every REQUIRED step. The input is an envelope plus (optionally) the raw evidence bytes; the output is a verdict with collected warnings. Each numbered step below maps to the left column of Fig 5.1.

Fig 5.1 — Verification procedure (§7.1): six steps, their fail/warn paths, and the verdict

Two important variants

  1. Without evidence bytes (§7.2): when checking only a signature database, Steps 2.1–2.4 are skipped and the result MUST report contentHashVerified: false.
  2. Offline (§7.3): after the discovery doc is fetched once and the key cached, every later envelope from that key verifies with no network access.
Why an expired key can still produce a valid signature

An expired validTo only WARNs. If a valid RFC 3161 timestamp proves the signature was created while the key was active (genTime < validTo), the warning clears. The signature was honestly produced; the key simply retired afterward. This is the whole point of binding the timestamp to the signature bytes.

§ 6
Multi-File Bundles & the Internal Manifest
BUNDLE

When evidence is several files (screenshots + PDFs + config exports), subject.type is compliance-evidence:bundle and the evidence is a ZIP. OES then provides two levels of integrity: a bundle-level hash over the whole ZIP, and per-file hashes in subject.files[]. Inside the ZIP, a REQUIRED manifest.json at the archive root carries the structured metadata an auditor reads, and its file hashes MUST mirror subject.files[] exactly.

Inner signatures & extension fields

  • Inner signatures (§8.6) are OPTIONAL. When an OES envelope ships alongside the bundle, the envelope already covers everything, so innerSignature is redundant and MAY be omitted. It exists for standalone/offline transfer of a bundle without an envelope.
  • When both are present, the inner signature MUST use the same key (matching publicKeyFingerprint) and is verified as a defense-in-depth check; a divergence is a high-severity warning (likely producer bug or tampering).
  • If neither signature is present, the bundle is reported UNSIGNED and hashes alone are relied on.
  • Extension fields (§8.7): producer-specific data MUST be carried under x-* prefixes (e.g. metadata.x-workspace-id). Verifiers MUST ignore unknown x-* fields but MUST reject unknown non-x-* top-level fields.
§ 7
Security Considerations & Pitfalls
SECURITY

These are the failure modes most likely to bite implementers. Several mirror normative MUSTs from §11; the rest are integration mistakes seen in practice.

Pitfall · Re-encoding before hashing

subject.contentHash covers the exact bytes received. Verifiers MUST hash the bytes as-is, never a transcoded or re-serialized version. For JSON/XML, byte-level comparison is required — semantic equivalence is not sufficient (§11.5).

Pitfall · Skipping unknown algorithms

A verifier MUST reject envelopes with an unrecognized proof.algorithm, not silently skip signature verification (§15.3). Silent skips turn a future algorithm into a forgery vector.

Pitfall · Trusting the fingerprint as a security identifier

The 16-hex fingerprint gives 64 bits of collision resistance — enough to route to the right key within one issuer's small key set, but it is not security-critical. The full public key is always fetched from discovery; never authenticate on the fingerprint alone (§11.6).

Pitfall · HTTP discovery in production

Discovery documents and verification endpoints MUST be served over HTTPS in production (§11.1). HTTP is acceptable only for local dev. A MITM on discovery substitutes the key and defeats the whole scheme.

Other normative security rules

  • Key storage (§11.2): platform keys in an HSM or encrypted env with restricted access; BYOK keeps the private key in the customer's control (issuer stores only the public key); cloud KMS performs signing inside the KMS service.
  • Clock skew (§11.3): allow 5 minutes when checking proof.created and timestamp.timestampedAt. TSA timestamps largely mitigate skew concerns.
  • Replay protection (§11.4): the id field gives envelope uniqueness; ingestors SHOULD track seen id values to detect replays.
§ 8
Reuse, Interop & Production Mapping
INTEROP

OES is designed so a third party can verify evidence with no relationship to the issuer. The flow below is the auditor path; GRC platforms and CI/CD pipelines follow the same shape (import → verify → display, optionally re-sign to extend a chain of custody).

Step 1 · Receive
Evidence file(s) + the OES envelope
Distributed side-by-side: evidence.zip + evidence.oes.json, plus a cached issuer-discovery.json.
↓
Step 2 · Verify
Run the §7 algorithm
~100 LOC reference verifier in Node or Python. No account, API key, or issuer relationship needed.
↓
Step 3 · Anchor trust
TSA timestamp + discovered key
The RFC 3161 timestamp from a recognized authority confirms when; the well-known key confirms who.
↓
Step 4 · Record
Put the verdict in workpapers
valid/invalid, timestamp, issuer. For chain of custody, a platform MAY emit its own envelope referencing the prior one via metadata.priorEnvelopes[].

Conformance, Open Questions & References
INDEX

Conformance (§16)

Conformant issuer: produces schema-valid envelopes (§3), hashes per §4.4, signs with §4.2 canonicalization, serves discovery per §5, uses a supported algorithm (§4.1).

Conformant verifier: implements every REQUIRED step of §7, fetches keys via §5, reports contentHashVerified: false when bytes are absent, and rejects unsupported algorithms rather than skipping.
